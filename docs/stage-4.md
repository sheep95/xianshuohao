# 阶段 4：创建、房间与认领

2026-11-18，本阶段目标达成。沿用阶段 2.5 的纸张、柔和绿色和小印章设计，完成真实房间流程。后端业务代码与文案库未改动。

## 实现范围

1. 首页新增“开始立宪”，携带当前示例空间进入 /create；另有房间码入口。首页不预取创建页，示例仍不发 API 请求。
2. /create 分三步：空间与时长、具体行为边界、五条确认。群名和昵称可不填；每个摩擦最多一个水位、最多五个摩擦，可以取消，换空间会清空旧选择。缺项按后端同样的默认规则补齐，明确标注补充建议并要求确认。
3. 主动点击“生成我的宪法”才创建与生成；禁用连点并用同步锁阻止重复提交。创建成功后保留 code；生成失败时进入同一房间继续。如果服务器返回的边界与确认稿不同，则先在房间重新展示，不直接生成。
4. /room/[code] 显示真实房间码、时长、人数和五条草案。访客先阅读，昵称加入后才能认领；同名不是同一身份。非成员看不到认领昵称。
5. 一人认领即显示已通过，同时说明不代表全员同意。一个人可认领多条，人数仍按实际参与者计算。刷新保留认领。
6. 换条先选“保留边界换说法”或同一摩擦的其他明确水位，再显示新旧动作、候选条文、执行接口与将清空的认领。需勾选确认才应用；已认领条目需创建者确认。替换后成为待议，需要重新认领。
7. 房间每 8 秒在页面可见时读取一次，恢复焦点及手动按钮也可刷新。写操作期间不发起新轮询，旧读取响应被序号隔离，避免覆盖写操作结果。
8. 房间邀请链接支持复制；剪贴板不可用时选中只读文本供手动复制。已有定稿房间可只读查看，不能认领、换条或新加入。本阶段没有定稿按钮或卡片导出页。

## 请求与恢复

统一客户端 room-api.ts 使用同源 Cookie、X-CSRF-Protection、12 秒网络等待上限和 no-store。此处 12 秒是 HTTP 等待上限，不是阶段 6 的模型调用预算。

生成/确认替换按原请求和版本保存幂等编号，在当前标签页 sessionStorage 中复用；存储被限制时使用内存回退。创建本身无后端幂等协议，因此不自动重试，未知结果时明确提示。生成成功但响应丢失，通过 GET 同一房间恢复；创建响应完全丢失且用户未取得房间码，仍无法在无账号条件下找回，属于现有 API 边界。

403/409 后刷新状态，废弃旧预览并要求重新阅读；网络错误后查询现状，确认未提交的换条可按原编号重试。如果查询发现条文已更新，旧预览按钮禁用。没有把“换一种说法”暗中当作降低行为门槛。

## 手动验收

1. 首页选一个场景，点“开始立宪”。选空间和时长，填写可选群名/昵称，下一步选 1–5 个具体边界。
2. 查看第三步的五条底稿；不足五条时明确看到补充建议，确认后点“生成我的宪法”。应进入真实 /room/十位码，看到 1 人已加入、五条未认领。
3. 认领第一条，看到“已通过”和“我已认领”；刷新仍保留。
4. 复制房间链接，用无痕窗口打开；先不显示认领者昵称。匿名加入后看到人数增加和真实认领信息。
5. 创建者点击“这条我做不到，换一条”，选择另一个边界，预览新旧差别，确认后看到“待议”、旧认领清空；重新认领即可通过。其他成员不能确认替换已有人认领的条文。

## 已知边界与下一阶段

- 尚未提供最终卡、定稿按钮、复制最终全文或图片导出；已全部认领时只提示草案已保存。
- AI 在阶段 6 接入，当前真实生成仍用模板；未部署公网，未实测 PostgreSQL。
- 不同浏览器是不同匿名身份，清除 Cookie 无法恢复创建者权限；创建前表单只在当前页面内保留，刷新会重置尚未保存的填写。
- 按同源 Cookie 工作，localhost 与 127.0.0.1 不混用。后端 health 中 stage=2 保持原值，因为本次没有修改后端接口版本。
- 8 秒轮询带来最多一个刷新周期的显示延迟；手动刷新可立即查询。尚未使用 WebSocket。
